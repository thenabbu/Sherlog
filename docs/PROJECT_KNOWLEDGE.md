# SAT-SA project knowledge guide

This guide explains SAT-SA from the point of view of someone new to the repository. It describes the code that is currently present, not only the intended product design.

## 1. What SAT-SA is

SAT-SA (Supervisory Analytics Tool for SOC Assessment) is an offline Python tool for reviewing periodic SOC submissions from Critical Sector Entities (CSEs). It helps a supervisor decide what deserves manual attention by:

1. validating submitted records;
2. converting them into predictable local Parquet files;
3. finding three explainable warning patterns;
4. ranking entities by weighted findings adjusted for alert volume; and
5. publishing findings together with the source rows and calculations that explain them.

It is an assessment aid. It is not a SIEM, a real-time alerting system, an enforcement engine, a cloud service, or an automated supervisory decision-maker. It has no database and no runtime network dependency.

## 2. The whole project in one picture

```text
Five CSV/JSON tables
        |
        v
  ingest + Pydantic validation
        |----------------------> normalized/rejects.json
        v
  local Parquet tables
        |
        v
  detect (two Parquet passes)
        |----------------------> flags.json + alert_volumes.json
        v
  score entities
        |----------------------> entity_scores.csv
        v
  report / explain
        |----------------------> report.json or terminal output

Streamlit workbench (app.py) drives the same CLI and displays these artifacts.
```

The normal pipeline is therefore a sequence of artifacts, not a long-lived in-memory application. Each stage can be run independently from the command line.

## 4. The data model

SAT-SA expects five logical tables. The plural table names are also the filenames used by the CLI.

### Entities

One row per CSE: `entity_id`, `name`, `peer_group`, and optional `sector`.

### Assets

One row per monitored asset: `asset_id`, owning `entity_id`, `criticality` (`critical`, `high`, `medium`, `low`), and optional `asset_type`.

### Alerts

One row per alert: IDs for the alert/entity/optional asset, `category`, `severity`, timestamps, `disposition`, escalation fields, and optional case ID.

Allowed severity values are `critical`, `high`, `medium`, and `low`. Allowed dispositions are `true_positive`, `false_positive`, `benign`, and `unresolved`.

The schema rejects an alert whose `closed_at` or `escalated_at` occurs before `created_at`. It does not reject unknown extra columns: `StrictRecord` is configured to ignore extras. This makes the input contract tolerant of additional export fields while still validating known fields.

### Cases

One row per case: case ID, entity ID, open/close timestamps, a list of alert IDs, and whether root cause was documented. In CSV, `alert_ids` is expected to be a JSON-encoded list.

### Escalations

One row per escalation: escalation ID, alert ID, timestamp, and destination tier.

Every row is validated with Pydantic. A bad row is not silently dropped; it is written to `rejects.json` with its source, table, row number, original normalized record, and validation error.

## 5. The command-line workflow

The installed console command is `satsa`, registered by `pyproject.toml` as `sat_sa.cli:app`. The equivalent development invocation is `python -m sat_sa.cli ...`.

### Generate synthetic data

```powershell
satsa generate-synth --entities 25 --alerts-per-entity 400 --seed 42 --out data/synth
```

The generator creates the five tables plus `ground_truth`. Synthetic data is deterministic for a given seed and injects known examples of all three detector conditions. Ground truth is only used by `validate`; detectors never read it.

### Ingest and validate

```powershell
satsa ingest --input data/synth --format csv --out data/normalized
```

The command finds the five supported table files, validates every row, and writes one Parquet file per table plus `rejects.json`. CSV is the scalable path: rows are read in bounded batches, optionally validated in a process pool, and appended as Parquet row groups. JSON is supported, but standard JSON arrays are loaded as one document and are less suitable for very large submissions.

### Detect

```powershell
satsa detect --data data/normalized \
  --detectors execution_gaps,negative_space \
  --config detector_config.yaml --out results/flags.json
```

Detection requires `alerts.parquet`, `entities.parquet`, and `assets.parquet`. It scans alerts twice:

- Pass 1 calculates closure-duration baselines and counts alert volume. Closure durations are stored in temporary binary files and read through NumPy memory maps, so all durations are not kept in RAM.
- Pass 2 creates D1/D2 flags per batch and aggregates only `(entity_id, asset_id)` counts for D3. Evidence is attached before the batch is discarded.

The command writes `flags.json` and `alert_volumes.json` beside the requested output. Flag IDs are renumbered globally after all detector groups finish.

### Score, report, and explain

```powershell
satsa score --flags results/flags.json --config detector_config.yaml \
  --out results/entity_scores.csv
satsa report --scores results/entity_scores.csv --flags results/flags.json \
  --format table --out results/report.json
satsa explain --entity-id CSE-003 --flags results/flags.json
```

`score` ranks entities. `report` combines each entity's score and flags into a JSON report and can print a Rich table. `explain` prints every finding and its evidence for one entity.

For a complete demo, use the command sequence in the root `README.md`.

## 6. The three detectors

### D1: `fast_closure`

Question: are high/critical alerts being closed unusually quickly, possibly without meaningful investigation?

For each severity, SAT-SA computes alert closure time:

```text
time_to_close_minutes = closed_at - created_at
lower_fence = Q1 - k × IQR
```

With the default `k = 1.5`, a high or critical alert is flagged when its closure time is below that severity's lower fence. The baseline stores Q1, IQR, and sample size. The finding includes the alert ID, observed duration, baseline values, and the source alert row.

### D2: `no_escalation`

Question: was a critical alert that was declared a true positive closed without escalation?

This is a deterministic rule:

```text
severity == critical
AND disposition == true_positive
AND escalated == false
```

Each matching alert produces a flag with a direct rationale and the source alert row. It does not use peer statistics.

### D3: `low_coverage`

Question: might a critical asset be a monitoring blind spot compared with similar entities?

SAT-SA looks at alerts in the most recent configured window (default 30 days). For each critical asset it compares observed alert count with the peer-group median:

```text
flag when observed_count < coverage_threshold_pct × peer_median
```

The default threshold is 25%. Assets with a zero peer median are not flagged because there is no positive comparison baseline. The finding includes asset ID, window, observed count, peer group, peer median, and the source asset row.

## 7. Benchmarking and scoring

`peer/benchmark.py` is deliberately detector-neutral. It reduces duplicate entity metrics to one median per entity, then calculates within each peer group:

- median;
- Q1 and Q3;
- IQR (`Q3 - Q1`); and
- percentile rank.

Entity scoring uses the weighted number of findings divided by a volume adjustment:

```text
risk_score = Σ(weight(detector) × flag_count(detector)) / log(1 + alert_volume)
```

Default weights are:

| Detector | Weight |
|---|---:|
| `fast_closure` | 2 |
| `no_escalation` | 3 |
| `low_coverage` | 2 |

Entities with no flags are still included when they appear in `alert_volumes.json`. Results sort by descending risk score, then by the number of distinct detector types triggered, then by entity ID. The rank is one-based.

## 8. What makes a finding explainable

`Flag` is the common output object. It contains:

- a globally unique `flag_id`;
- detector name;
- entity ID;
- severity weight;
- plain-English rationale;
- an evidence dictionary; and
- UTC generation time.

The evidence dictionary stores exact source IDs and detector-specific values. `attach_evidence()` then finds those IDs in the current alert or asset batch and adds JSON-safe `source_rows`. This is why a result can be reviewed later without reconstructing the original calculation from memory.

## 9. Runtime and large-data behaviour

`runtime.py` is local-only. It uses logical CPU count and available physical RAM. A zero `--batch-size` or `--workers` means automatic selection. Initial automatic batches are 10,000, 50,000, 100,000, or 200,000 depending on free RAM; automatic workers are bounded to at most 12 and usually use logical CPUs minus two.

Adaptive mode checks every four completed batches by default. Under critical memory pressure it halves the next batch and reduces admitted workers. With sustained headroom it can grow the batch by up to 25% and add a worker, within ceilings. `--no-adaptive` keeps the chosen settings fixed. `satsa system-info` shows the initial choice.

The important memory rule is that the full alert table is not loaded by the CLI detector. One bounded Parquet batch is active at a time, plus compact counters and temporary closure statistics. This is the main reason the project uses Parquet row groups and appenders.

## 10. The Streamlit workbench (`app.py`)

The UI is a presentation/orchestration layer, not a second analytics implementation.

When a user starts a run, `run_pipeline()` creates:

```text
runs/<sanitized-run-name>/
  meta.json
  source/
  normalized/
  results/
```

For a synthetic run, the UI calls `generate-synth`. For an uploaded run, it stages the five CSV files. It then calls, synchronously and with argument lists:

```text
ingest → detect → score → report
```

Synthetic runs also call `validate`. The UI captures command output, records step status in `meta.json`, and stops if a step fails.

The current page model includes Run assessment, Portfolio overview, Entity profile, Findings feed, Peer benchmarking, Review queue, Data health, Rules in effect, Report center, and How it works. Pages read Parquet/JSON/CSV artifacts from the active run. Review dispositions are appended to `results/dispositions.jsonl`; the review queue is stored in `results/review_queue.json`.

The UI sanitizes run names before using them as directories and does not shell-interpolate user input. Optional Plotly/Altair support is detected at runtime; the core package requirements do not declare those libraries, so the UI has fallbacks.

Run it with:

```powershell
streamlit run app.py
```

`detector_config.yaml` currently contains:

```yaml
fast_closure_k: 1.5
coverage_window_days: 30
coverage_threshold_pct: 0.25
investigation_duration_k: 1.5
low_entity_activity_pct: 0.25
recurrence_min_alerts: 3
workload_deviation_pct: 0.5
min_peer_sample: 4
weights:
  fast_closure: 2
  no_escalation: 3
  low_coverage: 2
```

Typical pipeline outputs are:

| File | Meaning |
|---|---|
| `normalized/*.parquet` | Accepted, validated local tables. |
| `normalized/rejects.json` | Audit trail for rejected rows. |
| `results/flags.json` | Self-contained findings and evidence. |
| `results/alert_volumes.json` | Alert counts by entity, used for scoring. |
| `results/entity_scores.csv` | Ranked entity scores. |
| `results/report.json` | Entity-centered report containing scores and flags. |
| `runs/<run>/meta.json` | UI run metadata, parameters, step results, and timestamps. |
| `runs/<run>/results/validation.txt` | Captured synthetic validation output. |
| `runs/<run>/results/dispositions.jsonl` | UI review decisions appended over time. |
| `runs/<run>/results/review_queue.json` | UI-managed manual review queue. |

## 12. How to change the project safely

If changing a field or validation rule, start in `sat_sa/schema.py`, then update input examples, the UI's `REQUIRED_COLS`, and relevant documentation.

If changing detector behaviour, put the calculation in the detector module, keep it file/network/CLI independent, update `detector_config.yaml` if a threshold changes, and preserve evidence fields. The CLI should only orchestrate it.

If changing ranking, update `sat_sa/scoring/core.py` and the UI's display assumptions together.

If changing input/output paths or concurrency, update `sat_sa/cli.py` and check both direct CLI use and `app.py`'s command construction.

If changing the UI, first identify whether the change is presentation-only. Do not reimplement detector or scoring logic in `app.py`; it should continue to invoke the CLI and read artifacts.

## 13. Verification checklist for a newcomer

Run the small pipeline from `README.md`, then inspect files in this order:

1. `data/synth/alerts.csv` to see source records;
2. `data/normalized/rejects.json` to confirm validation auditing;
3. `data/normalized/alerts.parquet` to see the normalized store;
4. `results/flags.json` to see rationales and source rows;
5. `results/entity_scores.csv` to see ranking; and
6. `results/report.json` to see the report assembled from scores and flags.

Useful code-reading entry points are `sat_sa/cli.py:110` for generation, `sat_sa/cli.py:142` for ingestion, `sat_sa/cli.py:252` for detection, `sat_sa/detectors/execution_gaps.py`, `sat_sa/detectors/negative_space.py`, and `app.py:1375` for the UI pipeline.
